# OpenDavki

**Open-source, local-first tax reporting for Slovenian investors.**
Broker statements in, validated eDavki XML out, every euro traceable.

## What it is

```
Broker statements ─▶ canonical ledger ─▶ Slovenian tax rules ─▶ validated eDavki XML
 (IBKR, Trading 212,   (trades, dividends,   (FIFO, EUR conversion,   (Doh-KDVP, Doh-Div,
  Revolut, ...)          transfers, splits)    withholding tax)         checked against FURS XSDs)
```

Principles:

- **Traceable.** Never produce a number that cannot be explained and traced back to a line of the original statement.
  Every ledger entry carries its source file (SHA-256) and line.
- **No silent loss.** Importers must account for every row: mapped, skipped with a stated reason, or failed with an error.
- **Local-first.** Statements and declarations stay on your machine. No accounts, no uploads.
- **Auditable.** Open calculations; `BigDecimal` only, never floating point.
- **Dividends and capital gains stay separate.** Losses are never netted against dividend income.
- **Schema-valid is not tax-correct.** Output is validated against the official FURS XSDs *and* meant to be verified
  against real examples.

## Run it

### Packaged application (no Java, Maven or Node)

The packaging scripts produce self-contained app images with their own Java runtime, the web interface and the official
XSDs. When the project publishes release artifacts, unzip or untar the one for your platform; you can build the same
artifact locally with `./packaging/package.ps1` or `./packaging/package.sh`. Then:

- **Windows:** unzip, open the `OpenDavki` folder and double-click `OpenDavki.exe` (browser client), or the
  `OpenDavkiDesktop` folder and `OpenDavkiDesktop.exe` (native JavaFX window).
- **macOS:** open `OpenDavki.app` or `OpenDavkiDesktop.app`. The build is unsigned, so the first launch needs
  right-click → Open (or the Gatekeeper instructions in [docs/desktop.md](docs/desktop.md)).
- **Linux:** run `OpenDavki/bin/OpenDavki` or `OpenDavkiDesktop/bin/OpenDavkiDesktop`.

Both clients start the same local server on `127.0.0.1` only and use the same settings and ledger. The browser client
opens the browser and shows a tray icon with **Open** and **Quit**; the desktop client opens a JavaFX window with
File → Open in browser, File → Quit and View → Reload. Settings and caches live in the OS user directories;
`OpenDavki paths` and `OpenDavki doctor` show exactly where. Nothing is uploaded.

### From source

Requires JDK 21. Node 22 is needed only to build the web interface; the Maven wrapper is included, so a global Maven
install is not required.

```bash
./build.ps1                 # Windows; frontend + Java in one command
./build.sh                  # macOS/Linux
./run.ps1                   # no arguments: start the interface and open the browser
java -jar backend/desktop/target/opendavki-desktop.jar   # native JavaFX window
```

The built jar also works from any directory:

```bash
J="java -jar backend/cli/target/opendavki.jar"   # run from the repository root for the example paths below
$J serve                                     # start on 127.0.0.1 and print the keyed address; add --open to open it
$J adapters                                  # importers on the classpath
$J import statement.csv -o ledger.json       # read, de-duplicate, check (exit code 1 on errors)
$J check ledger.json
$J describe statement.csv                      # layout of a statement without its contents (safe to share)
$J import statement.csv --profile my-profile.json -o ledger.json   # a CSV broker described by a JSON profile
$J fx USD 2024-03-01 100                     # rate the configured source gives, and 100 USD in EUR

# ledger -> declarations for a tax year (XML validated against the XSDs, plus audit-<year>.json and audit-<year>.md)
$J report ledger.json --year 2024 --tax-number 12345678 --out-dir out

$J audit out/audit-2024.json                 # render the readable audit report again from the JSON
$J validate KDVP out/kdvp-2024.xml
$J generate KDVP examples/kdvp-synthetic.json -o kdvp.out.xml   # from a hand-written report (dev tool)
```

Try the whole pipeline offline on synthetic data (own rates file instead of the ECB download):

```bash
./build.ps1                                  # or ./build.sh
./run.ps1 import examples/statement-generic.csv -o ledger.json
./run.ps1 report ledger.json --year 2024 --tax-number 12345678 --out-dir out --env-file examples/synthetic.env
```

`--schema-dir`, `--env-file` and `--web-dir` remain available as overrides. Without them the application finds
`./schemas`, `./.env` and the built interface when they exist, and otherwise uses the bundled XSDs and the user config
directory.

Exit codes: `0` ok, `1` XSD validation failed or ledger errors, `2` input/config error, `3` schema or rate source unavailable.

`report` refuses to write XML when any instrument or payment had to be left out because of an error; `--allow-incomplete` writes the partial result for inspection only.

## Configuration

Copy [`.env.example`](.env.example) to `.env` (git-ignored), or let the packaged application use its per-user settings
file. Resolution order: `--env-file`, then `OPENDAVKI_ENV_FILE`, then `./.env`, then the user config directory. Real
environment variables override the file. `opendavki paths` prints the resolved paths.

| Setting | Default | Meaning |
|---|---|---|
| `OPENDAVKI_HOME` | unset | Portable mode: config, cache, schema cache and rate cache live under this one directory (process environment only) |
| `OPENDAVKI_ENV_FILE` | unset | Settings file to use instead of `./.env` (process environment only) |
| `OPENDAVKI_SCHEMA_DIR` | unset | Official XSD directory to use instead of `./schemas` or the bundled copy (process environment only) |
| `OPENDAVKI_FX_SOURCE` | `ECB` | `ECB`, `BSI` (Bank of Slovenia) or `FILE` (your own CSV) |
| `OPENDAVKI_FX_MISSING_DAY` | `PREVIOUS` | use the latest earlier rate when a day has none, or `FAIL` |
| `OPENDAVKI_FX_MAX_LOOKBACK_DAYS` | `7` | limit for the fallback above |
| `OPENDAVKI_FX_CACHE_DIR` | user cache directory (`OpenDavki/fx`) | download cache; `./.opendavki/cache/fx` is still honoured when set explicitly |
| `OPENDAVKI_FX_ECB_URL`, `_BSI_URL`, `_FILE` | ECB history URL, empty, empty | source locations |
| `OPENDAVKI_INSTRUMENTS_FILE` | empty | CSV that fixes missing ISINs and asset classes ([docs/instrument-master.md](docs/instrument-master.md)) |
| `OPENDAVKI_OVERRIDES_FILE` | empty | CSV that drops individual ledger entries, each with a reason ([docs/overrides.md](docs/overrides.md)) |
| `OPENDAVKI_TIMEZONE` | `UTC` | zone used to turn timestamps with an offset into dates (Trading 212) |
| `OPENDAVKI_INTEREST_TYPE_CODE` | _(unset)_ | Doh-Obr interest type code written on every interest row; unset omits it with a warning (unverified, D-12) |
| `OPENDAVKI_INCLUDE_FEES` | `true` | add broker fees to purchase cost and deduct them from sale value (unverified rule, see docs/tax-engine.md) |

Details, and why ECB is the default, in [docs/fx.md](docs/fx.md).

## Official schemas

`schemas/` holds `Doh_KDVP_9.xsd`, `Doh_Div_3.xsd` and `EDP-Common-1.xsd` as published by FURS (checksums in
`SHA256SUMS`); all tests validate against them. Constructs a sheet type cannot express (for example F10/F11 on a short
sheet) are rejected instead of dropped, and a sale larger than the held quantity fails instead of being exported.

## Known limitations

Full list with IDs and planned tickets: **[docs/BACKLOG.md](docs/BACKLOG.md)**. What is blocked on a decision, a document or a file of yours, and what to do about it: **[docs/BLOCKERS.md](docs/BLOCKERS.md)**.

- **Tax engine unverified**: FIFO, EUR conversion, fee treatment and the sheet layout (open lots carried into the year, split restating) follow assumptions that are not confirmed against ZDoh-2/FURS and were tested only on hand-computed synthetic cases (T-01 to T-03, T-08, T-09).
- **Tax engine gaps**: only plain `PLVP` sheets; no F10, per-item foreign tax or loss transfer; Doh-Div lacks payer address and tax number; an unsupported corporate action or a missing purchase excludes the instrument (T-04 to T-07, T-10, T-11).
- **Never validated end to end**: generated XML has not been imported into eDavki or compared with a hand-prepared declaration (D-01).
- **Draft importers**: the Revolut and DEGIRO profiles were written from memory and have never met a real file; every report that uses them says so (P-01 to P-04).
- **Importers barely verified**: Trading 212 was checked against one real export (not committed), IBKR only against a synthetic statement written from its documented layout; no other broker has a sample (I-01, I-02, R-01 to R-06, S-01, [docs/sample-data.md](docs/sample-data.md)).
- **Exchange rates**: the ECB reference rates are the source the maintainers state FURS recommends, but the FURS document was not read; the Bank of Slovenia source has no default URL, the ECB download was never run live, and the rate-date and rounding rules are undecided (X-02 to X-05).
- **Corporate actions**: splits (forward and reverse) and hand-entered conversions are applied ([docs](docs/corporate-actions.md)); the tax-neutral treatment of conversions is unverified, mergers with cash, spin-offs and similar are not modelled, and broker adapters do not produce conversions themselves (L-04, I-05, C-01 to C-04).
- **Incoming transfers from a broker that is not imported have no cost basis** unless the ledger is edited by hand (I-08).
- **Out of scope for now**: options, futures, CFDs, crypto, other eDavki forms, signing/submission (D-09, I-04, I-10, D-11); interest (Doh-Obr) is generated but its type code and payer details are unverified (D-12).
- **Only original filings** are produced; corrections and late submissions are partly modelled (D-04).
- **Audit report and Java diagnostics** are English only; the interface itself switches between English and Slovenian, and the audit is Markdown shown as text (A-01, U-01).
- **Desktop packaging** is a portable app image, not a signed installer: Windows SmartScreen and macOS Gatekeeper warn about the unsigned build, there is no auto-update, MSI/DMG signing or icon identity yet. CI builds both clients for all platforms and launch-probes them, but nobody has opened the UI on a real macOS or Linux desktop yet (U-05 to U-09).
- **The JavaFX shell** uses a legacy IIFE bundle, a native file picker and a download bridge; CI smoke-tests it on all four packages (Linux under Xvfb). Nobody has yet clicked through it on a real macOS or Linux desktop, so the browser client remains the fallback (ODV-013, U-09).
- **Saved profiles are stored but not offered as a picker** on the import screen; a profile file is still chosen per import (U-10).
- **No license file yet**; the CI workflow has run and passes (L-10, see [BLOCKERS](docs/BLOCKERS.md)).
